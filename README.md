# Proxmox VM → OVF/VMDK Exporter

A small Bash script that exports a Proxmox VE virtual machine into a **matching OVF + streamOptimized VMDK** pair for importing into another virtualization platform.

Designed to be simple: run it on a Proxmox node, enter a VM ID, and the script handles the shutdown, disk conversion, and OVF generation.

## ✨ Features

- Interactive VM ID prompt
- Optional VM ID argument for automation
- Verifies that the VM exists before doing anything
- Detects the first `scsi`, `sata`, `virtio`, or `ide` disk
- Reads the VM's configured CPU, RAM, and disk size
- Gracefully shuts down a running VM
- Waits for the VM to stop before exporting
- Converts the disk to **streamOptimized VMDK** with `qemu-img`
- Generates an OVF descriptor matching the exported VMDK
- Keeps RAM units correct for OVF imports
- Saves everything under `/export-files`
- Does **not** force-stop a VM if graceful shutdown fails
- Leaves the VM powered off after a successful export

## 🚀 Quick start

Run directly from GitHub without cloning the repository:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/libre-data/pve-vm-to-ovf/main/export-ovf.sh)
```

You will be prompted for the VM ID:

```text
Enter VM ID to export: 100
```

### Or specify the VM ID directly

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/libre-data/pve-vm-to-ovf/main/export-ovf.sh) 100
```

> **Why `bash <(curl ...)` instead of `curl ... | bash`?**
> The script is interactive and needs your terminal for input. Bash process substitution lets the script read from the terminal normally.

## 📦 Output

For a VM named `migrate-test`, the script creates:

```text
/export-files/migrate-test.ovf
/export-files/migrate-test.vmdk
```

The OVF references the VMDK using the correct virtual disk size and the VM's configured RAM and CPU count.

The VMDK is sparse/stream-optimized, so the file's physical size can be much smaller than its configured virtual capacity. For example, a 50 GiB virtual disk may initially occupy only a few GiB on the export filesystem.

## 🖥️ Importing the VM

The resulting files are intended for OVF/VMDK import workflows.

Typically, in your destination platform:

1. Open **Import Virtual Machine**.
2. Select **OVF** as the template/file type.
3. Upload the generated `.ovf` file.
4. Upload the matching `.vmdk` file.
5. Leave the manifest/MF field empty unless your destination explicitly requires one.
6. Select the destination storage/location.
7. Start the import.

**Always upload the OVF and VMDK generated by the same export.** The OVF contains metadata describing the VMDK, so mixing files from different exports can cause errors such as a VMDK count or descriptor mismatch.

## Requirements

Run the script on a **Proxmox VE node as root**.

Required commands:

- `qm`
- `pvesm`
- `qemu-img`
- `python3`

These are normally available on a standard Proxmox VE installation.

## 🔄 What the script does

For a VM ID such as `100`, the workflow is:

```text
VM ID
  │
  ├─ Verify VM exists
  ├─ Read VM name / CPU / RAM / disk
  ├─ Gracefully shut down VM
  ├─ Convert Proxmox disk → streamOptimized VMDK
  ├─ Generate matching OVF
  └─ Save OVF + VMDK in /export-files
```

If the VM is already powered off, the shutdown step is skipped.

If a running VM does not shut down within the timeout, the script stops and **does not force power it off**. This is intentional to avoid unexpected data loss.

## ⚠️ Important limitations

### One disk only

The current version exports **only the first attached virtual disk**.

If the VM has multiple `scsi`, `sata`, `virtio`, or `ide` disks, the script prints a warning and exports only the first one.

For example:

```text
WARNING: VM has multiple supported disks. Only the first disk will be exported.
```

Multi-disk export is not currently supported.

### Network configuration

The OVF contains a generic `VM Network` connection.

It does **not** reproduce Proxmox-specific settings exactly, such as:

- `vmbr0` bridge configuration
- Proxmox firewall settings
- VLAN configuration
- Exact Proxmox network device model/settings

The destination platform may therefore require network settings to be adjusted after import.

### VM hardware configuration

The export is focused on portability rather than a byte-for-byte recreation of the Proxmox VM configuration. Some Proxmox-specific settings are intentionally not represented in the OVF.

### Snapshots

The script exports the selected disk's current state. It is not a snapshot-management or snapshot-conversion tool.

## 🛑 VM shutdown behavior

A running VM is shut down with:

```bash
qm shutdown <VMID>
```

The script waits up to 120 seconds for the VM to stop.

If the VM does not stop in time, the export is aborted rather than using a hard power-off.

After a successful export, the VM remains powered off.

Start it again manually if required:

```bash
qm start <VMID>
```

## 💾 Disk conversion

The disk is converted with:

```bash
qemu-img convert -p -O vmdk -o subformat=streamOptimized <source> <destination>
```

`streamOptimized` is used because it is well suited to OVF-based portability/import workflows.

The exported VMDK can be much smaller than the VM's virtual disk capacity because it is sparse/stream-optimized.

## 🧠 RAM and CPU

The script reads the VM's Proxmox configuration and writes the relevant values into the OVF.

For example, a Proxmox configuration such as:

```text
memory: 9000
cores: 1
```

means **9000 MiB of RAM and 1 virtual CPU**. The OVF represents memory in bytes, avoiding the common mistake of accidentally describing 9000 MiB as 9 MB.

## 🧪 Example

Given a Proxmox VM:

```text
VM ID: 100
Name: migrate-test
RAM: 9000 MiB
CPU: 1 core
Disk: 50 GiB
```

Run:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/libre-data/pve-vm-to-ovf/main/export-ovf.sh) 100
```

The result is:

```text
/export-files/migrate-test.ovf
/export-files/migrate-test.vmdk
```

These two files can then be uploaded together to an OVF/VMDK importer.

## 🔧 Troubleshooting

### `ERROR: VM ID must be a number.`

If using the interactive version, make sure you run it with:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/libre-data/pve-vm-to-ovf/main/export-ovf.sh)
```

Avoid:

```bash
curl -fsSL https://raw.githubusercontent.com/libre-data/pve-vm-to-ovf/main/export-ovf.sh | bash
```

because the pipeline consumes standard input that the interactive prompt needs.

You can also avoid interactive input completely:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/libre-data/pve-vm-to-ovf/main/export-ovf.sh) 100
```

### Importer reports an OVF/VMDK mismatch

Make sure you are uploading the `.ovf` and `.vmdk` produced by the **same export run** and that the VMDK has not been renamed independently of the OVF.

### VM does not shut down

The script intentionally does not force-stop the VM. Shut it down manually, investigate why it is not responding, and run the export again:

```bash
qm shutdown <VMID>
```

### Not enough space in `/export-files`

The exported VMDK is sparse/stream-optimized, but the export still requires enough free space for the resulting file and temporary conversion activity. Check available space with:

```bash
df -h /export-files
```

## 🔐 Safety notes

This script is intended to make VM portability straightforward, but exporting a VM is still a potentially destructive operation if the source is modified during conversion.

For best results:

- Export during a maintenance window.
- Let the script shut the VM down cleanly.
- Keep a real backup of important VMs.
- Verify the exported files before deleting or modifying the original VM.

This project does **not** replace Proxmox Backup Server or a proper backup strategy.
